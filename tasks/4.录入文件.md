材料显示：

- `wiki/reference/reindex-v0.1-standard.md` 已明确最终 Node、目录、PDF、表格、图片、溯源和校验规则。新系统应编译到该协议，不另造产物协议。
- server 代码已具备 collection、raw 上传下载、包导入、browse/get、search/grep 和 DuckDB table query；数据库是派生服务层。
- `packages/cli` 目前只有 `doctor`；`testbase/test1/build_reindex.py` 是针对一个 PDF 的硬编码构建器，不是通用解析系统。
- 当前 server importer 尚未实现标准要求的全部严格校验。builder 和 importer 必须先共用同一协议实现，避免两个标准。
- Loom 值得复用 content hash 增量、机器事实与人工内容分权、stale 和 generated-file ownership；不复用其 path-derived ID 或另一套 card 协议。
- table_demo 值得复用全页检查、结构化 evidence、可恢复状态机、修复后独立复审和 `HUMAN_REVIEW`；它只作为 PDF table stage，不作为总编排器。
- 2026-07-26 调研的 CocoIndex v1.0.14 已提供输入/代码变化检测、函数 memo 和 processing component，但它的 target-state 模型不能替代 ReIndex 的稳定 UUID、人工审阅、整包校验和原子发布。

## 总方案

### 1. 产品定义与边界

把 raw → ReIndex 定义为一个本地优先、协议优先、可恢复的编译系统：

```text
raw inventory
→ probe / route
→ typed parser pipeline
→ evidence + Node drafts
→ Agent / human review
→ identity + assemble
→ strict validate
→ atomic commit
→ 可选上传现有 server
```

核心边界：

1. `reIndex/` 只保存合法的 `reindex/node@0.1` 包；cache、任务、prompt、运行记录和 parser 版本都在 `.reindex/`。
2. `rei` 负责完整枚举、hash、调度、缓存、身份、写包和校验；Agent 负责理解目标、语义补全、视觉审核和异常修复。
3. Agent 和 parser 都不能直接写最终 `.node.md`。它们提交有 Schema 的 draft/evidence，由核心 assembler 统一写包。
4. 构建和上传分开。`READY` 只表示本地包通过严格校验；只有用户明确要求时才发布。
5. 任何失败或不可靠证据都不修改上一个 READY 包，不伪造内容。

首期不做向量/全文索引、不让 server 执行用户 parser、不默认联网、不猜主外键、不承诺所有二进制文件都能自动高质量理解。

### 2. 用户与 Agent 工作流

主命令使用 `rei`；现有 `reindex` 暂时保留兼容入口。

```bash
rei init ./raw --output ./reIndex
rei plan --json
rei build --json
rei status --json
```

若 `build` 返回 `NEEDS_AGENT`，当前宿主 Agent 继续：

```bash
rei task next --json
rei task show <task-id>
rei task submit <task-id> --from submission.json
rei build --resume --json
```

完成后：

```bash
rei validate --strict --json
rei diff --against last-ready
rei pack --output dist/package.zip
```

可选发布：

```bash
rei publish --server <url> --collection <uuid>
```

`--json` 的 stdout 只输出一个带版本的 JSON object，日志写 stderr。`NEEDS_AGENT`/`HUMAN_REVIEW` 是成功保存的工作流状态，不冒充 `READY`；默认不因可恢复暂停让普通 Agent 把命令误判为崩溃，CI 使用 `--require-ready` 获得非零退出码。

### 3. 项目文件

项目根目录保存 `raw/`、`reindex.toml` 和最近一个 READY 的 `reIndex/`。包外的 `.reindex/` 保存 `state.sqlite`、`identity.sqlite`、内容寻址 cache、每次 run 的 plan/events/evidence/tasks/staging，以及 `last-ready` manifest。

`reindex.toml` 保存可执行配置；raw 内的 `reIndex.md` 只作目录说明和解析上下文。生成目录不接受无追踪手改；人工/Agent 修订保存为带 `based_on` digest 的版本化 override，上游变化后自动 stale。

### 4. 代码分层

先建立以下边界：

```text
packages/core      Node model、严格 YAML、writer、validator、canonical hash
packages/compiler  discovery、IR、pipeline、cache、identity、task、assembler
packages/cli       rei 命令、JSON 输出、可选 server client
packages/server    复用 core validator，继续负责 revision、索引和查询
```

compiler 首期可作为 CLI 内部模块；但 `core` 必须独立，CLI 和 server 不得各维护一份 validator。

### 5. Pipeline 与中间模型

固定宏观阶段：

```text
discover → fingerprint → probe → route → extract → normalize
→ structure → enrich → review → identity → assemble → validate → commit
```

stage 只交换不可变、版本化 artifact：

- `SourceRecord`：相对路径、MIME、sha256、size、stat hint。
- `ArtifactRef`：类型、schema、digest、producer、inputs、locator。
- `NodeDraft`：logical key、kind、正文/资源/table draft、evidence、confidence、warnings。
- `ReviewTask`：basis hash、角色、instructions digest、evidence、result schema、允许写入范围。
- `BuildManifest`：输入清单、stage/action key、输出 ownership、Node basis、validation 和 package tree hash。

assembler 独占最终 UUID、路径、PDF child 编号、frontmatter、Preview、资源 hash 和树关系。运行期模型不写入 v0.1 Node。

### 6. 解析器扩展

解析器通过 Python entry point `reindex.parsers` 注册；可复用 parser 作为独立包，项目专用 parser 必须在配置中显式启用。外部命令 parser 使用 JSON 协议。

每个 parser 声明 ID/version、输入输出及配置 Schema、probe/route 优先级、cache policy、network/GPU/subprocess/Agent capability 和资源上限。

接口为 `probe → plan → run → resume`。用户 path rule 优先于 MIME，MIME 优先于扩展名；路由冲突在 `rei plan` 报错，不依赖插件加载顺序猜测。

第三方 parser 默认子进程隔离：source 只读，只写 run-specific 目录，默认无网络，清理 secret 环境变量。内置 parser 首期可同进程运行，但必须通过同一 conformance suite。

配置用 `[[routes]]` 把 glob/MIME 映射到 pipeline，并在 parser 段选择实现、参数和 `human-review` 等策略；默认 `network = false`。

### 7. 默认解析策略

- 目录：每个真实目录生成 `group/index.node.md`；就近 `reIndex.md` 提供说明。
- Markdown/TXT：一个 `text` Node，保留完整正文；编码问题产生 warning。
- CSV/TSV：精确 header/row count、保守类型、确定性最多 5 行 Preview；代码和前导零列保持 string；PK/FK 默认空。
- 图片：原图作为 source，OCR 和视觉描述分别保留 evidence；无法可靠描述时进入 review。
- 未知文件：server 补齐 `kind:file` 后生成保守说明，否则进入 unsupported review。
- PDF：page render/native words/outline/layout → 小 PDF 单 text 或大 PDF group + 完整有序 children → 表/图提取 → 冲突消解 → assemble。group 不复制 children 全文。
- PDF table：table_demo 作为可替换 stage，保留全页 inspection、cell evidence、跨页合并、repair、独立 recheck 和 `HUMAN_REVIEW`；验证通过后才转换为标准 CSV、table Node 和同编号 visual reference。

同页正文、表格和图片必须按 region/evidence 去重；最终编号由 assembler 统一分配，单个 parser 不自行占用 `0003`。

### 8. Agent 状态机

```text
PLANNED → RUNNING → NEEDS_AGENT / HUMAN_REVIEW
→ RUNNING → VALIDATING → READY
```

任务类型包括 PDF structure review、table inspection/repair/recheck、image description、table semantics 和 identity ambiguity。

每个任务的 `basis_hash` 覆盖 source、parser/version/config、instructions 和相关 draft；任一变化使旧提交 stale。修复者与独立复审者是不同角色，复审默认看不到修复理由。文档内容一律视为数据而非工作流指令，防止 prompt injection。

通用 `rei` 默认不自行再启动 Codex。未来可增加 `--agent-driver codex`，但它只能驱动相同 task 协议。table_demo 若保留自启动隔离复审，必须是显式配置的 parser capability。

### 9. 增量、身份与原子性

每个 stage 的 action key：

```text
SHA256(
  stage id/version + implementation digest + canonical config
  + ordered input artifact hashes + context/prompt/model profile
)
```

源扫描先用 path/size/mtime/ctime 快速复用旧 SHA，任一变化时重新流式 hash；正确性只信内容 hash。

失效规则：

- raw 未变：整个 source 子图命中 cache；
- 只改 `reIndex.md` 或 override：保留昂贵 extraction，只重做依赖的 enrich/assemble；
- parser/config/prompt 变化：从相应 stage 向下失效；
- PDF 改变：先按整文件正确失效，后续再增加 page artifact 级复用；
- 删除只移除 manifest 中由 rei 拥有且 digest 未被用户修改的输出。

Node ID 不能是 path/hash。`identity.sqlite` 持久化随机 UUID、source identity、parser namespace、semantic key 和历史 anchor：

- 同路径内容更新保留 source identity；
- 旧路径消失且新路径 hash 唯一匹配时视为 rename；
- 相同 hash 多副本或模糊 child 匹配进入 identity review；
- PDF child 用 outline/标题/邻域/table header/几何等 semantic anchor 匹配；
- 高置信一对一匹配保留 UUID，低置信宁可新建，不错误合并。

stage 在临时目录执行，成功并校 hash 后才写不可变 CAS。完整 staging 包严格校验后，在同文件系统事务式替换正式输出；失败时回滚，保留 last-ready 和可恢复现场。CAS GC 只删除从 READY、未完成 run、override 和 pinned manifest 不可达的对象。

### 10. CocoIndex 决策

MVP 不把 CocoIndex 设为硬依赖。原因不是它没有增量能力，而是 ReIndex 的主要难点仍需自己实现：

- 稳定 UUID 与跨重命名匹配；
- Agent review/stale/evidence；
- v0.1 Node/tree/table 语义；
- whole-package strict validation；
- 最终目录原子发布；
- 可导出的 build manifest 和安全插件边界。

先定义 `ExecutionEngine/StateStore` 接口并实现本地 SQLite + CAS。后续做 CocoIndex adapter PoC，比较冷构建、无变化、单文件/单页变化、删除、rename、parser/prompt 变化、kill 恢复、GC 和包一致性。只有产生相同 canonical package、相同失效与失败语义且明显降低复杂度时才采用；即使采用，也只替换执行/cache 层。

参考调研：CocoIndex 官方的 [core concepts](https://cocoindex.io/docs/programming_guide/core_concepts)、[function memo](https://cocoindex.io/docs/programming_guide/function/) 和 [processing component](https://cocoindex.io/docs/programming_guide/processing_component/)。

### 11. 实施顺序

#### M0：协议收口

- 新建共享 core：严格 frontmatter、Node Schema、canonical writer/hash、完整 package validator。
- CLI validate 和 server import 共用；补齐 `kind:file`、raw CSV query 和过时文档。
- 把协议每条规则做成正反 conformance fixtures。

#### M1：确定性本地纵向切片

- `rei init/plan/build/status/explain/validate/diff/pack`。
- SQLite state、CAS、identity、ownership、staging commit。
- 支持目录、Markdown/TXT、CSV。
- 验收无变化二次构建 0 parser rerun，单 CSV 只失效相关子图。

#### M2：PDF 与图片

- PyMuPDF probe/native text/layout/outline、small/large PDF、ordered children、image/OCR。
- 现有 Bielefeld fixture 不依赖业务硬编码生成同等语义包。

#### M3：Agent 任务与 table_demo

- task show/submit/resume、basis stale、HUMAN_REVIEW、独立复审。
- table_demo adapter 和 PDF table evidence。

#### M4：插件 SDK

- entry point/command parser、capability allowlist、隔离和 conformance kit。
- 给一个 glob 定制 parser 不需要改 core。

#### M5：发布与规模化

- `rei publish`、远程 raw/version import 契约、失败不影响旧 revision。
- 大目录并行、cache verify/GC；独立完成 CocoIndex PoC/ADR。

### 12. 验收条件

1. 混合 raw 目录可由 Agent 驱动生成严格合法包并导入现有 server。
2. 相同 raw/config/toolchain/冻结 Agent 提交生成 byte-identical package tree。
3. 无变化重建不运行 parser；mtime 单独变化不改变输出。
4. 单文件修改、删除、rename、parser/config/prompt/override 变化具有精确失效测试。
5. Node UUID 在明确的内容更新和唯一 rename 中保持；歧义不自动误配。
6. 中断、parser crash、校验失败和 `HUMAN_REVIEW` 都不改变 last-ready。
7. 所有 Node 回链合法 source/resource hash 和 locator；CSV Preview 逐字来自完整 CSV。
8. 大 PDF children 完整覆盖正文且无重复聚合全文；PDF 表格没有漏页审查。
9. Agent submission 受 Schema、basis 和 evidence 约束，不能越权写包或编造机器事实。
10. 自定义 parser 可独立安装、配置、检查和增量失效。
11. builder 与 server 对同一 conformance fixture 给出一致校验结果。
12. 现有 search-eval 不退化，但“能搜到”不能代替解析正确性指标。

## 主要风险与处理

- PDF/OCR 长尾：证据链、独立复审、`HUMAN_REVIEW` 收口，不承诺万能自动化。
- AI 幻觉：机器事实不可由 AI 改；语义输出带 evidence；PK/FK 禁猜。
- cache 伪命中：代码、依赖、配置、prompt、模型和 context 全进入 action key，并提供 explain/verify。
- ID 误合并：低置信宁可新 UUID 或人审。
- 用户手改被覆盖：generated output + versioned override + digest 冲突保护。
- 插件与隐私：显式 allowlist/capability，默认离线，限制写目录、网络、资源和 secret。
- 协议再次分叉：共享 core、同一 conformance suite、CI gate。
