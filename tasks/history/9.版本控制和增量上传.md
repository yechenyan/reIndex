## 当前实现判断

- CLI 每次把完整 package 和全部被引用 sources 分别打成 ZIP，`POST /v1/push` 一次上传。
- 服务端已经把文件按 SHA-256 存入全局内容寻址目录，所以相同字节不会重复落盘；但网络仍重复上传，
  所有 Node、SearchUnit 和 embedding 也会重建。
- 服务端用一个数据库事务替换 Collection 当前态，失败不会破坏旧当前态；`package_hash` 已能标识完整快照，
  `node_hash` 已能发现 Node 卡片和资源内容变化。
- `.rei/remote.json` 已记录上次成功 push 的 `package_hash`，可以直接作为客户端的 base version。
- 当前 `node_hash` 不含派生的 path、parent、tree/order path。服务端做增量投影时不能只比较 `node_hash`，
  还要比较完整投影字段，或计算仅供服务端使用的 `projection_hash`。

因此问题分为两个独立层次：

1. **增量传输**：只上传服务端尚不存在的字节。
2. **增量索引与版本历史**：只重算变化投影，并决定旧快照能否回滚。

前者不要求保留历史；后者也不应该要求复制每一版的全部对象和搜索索引。

## 可选方案

| 方案 | 做法 | 优点 | 缺点 | 适用情况 |
| --- | --- | --- | --- | --- |
| A. 当前态 + 增量 blob | 服务端只保留当前态；客户端先发送完整文件 manifest，服务端返回缺失 SHA-256，再上传缺失对象并提交 | 最简单；立刻减少上传带宽；继续使用当前数据库模型 | 无回滚和审计；增量索引仍需另做 | 只关心发布最新数据 |
| B. CAS + 轻量快照（推荐） | A 的基础上，每次成功提交保存不可变版本记录和完整 manifest；当前表只投影 active version | 上传去重、乐观并发、回滚和审计同时具备；旧版复用相同 blob；搜索仍只服务当前态 | 多两张左右的元数据表；必须做保留策略和 GC | 当前 ReIndex 的最佳平衡 |
| C. Loom/Git 式完整 revision | 每版保存完整 Node/resource/search 投影，支持 pull delta、分支、merge/rebase 和历史查询 | 协作和 time travel 最强；任意版本可立即查询 | 表规模约随版本数增长；索引与 embedding 重复；冲突语义复杂 | 明确需要多人协作或历史版本在线查询 |
| D. ZIP/rsync 分块差量 | 对整个 ZIP 或大文件做二进制块级差分 | 单个超大、局部变化文件可能节省更多流量 | ZIP 压缩后不稳定；服务端无法直接理解 Node/resource 变化；实现和恢复复杂 | 以后针对超大二进制文件优化 |

不建议把 C 作为第一版。Loom 面向可协作 workspace，依赖本地 Git、base revision、三方合并和 rebase；
ReIndex 当前是“编译完整 package 后发布为服务端检索当前态”，冲突时拒绝陈旧提交并要求重新 pull/scan/push
已经足够。CocoIndex 的可借鉴点是“目标态由源状态决定、只重算变化、按处理单元原子更新、对未变化函数结果
做 memoization”，没有必要引入它的通用数据流运行时。

## 推荐方案

采用 **B：完整状态 manifest + 缺失 blob 上传 + 原子切换当前版本 + 有界轻量历史**。

关键原则：

1. ReIndex package 仍是协议真相；新增 manifest 只是传输协议，不进入 `.node.md`。
2. 客户端每次提交完整“期望状态”manifest，而不是只声明 patch；删除由新 manifest 中缺失的路径推导。
3. 文件字节按 SHA-256 不可变寻址；logical path、role 和 Collection 归属仍在数据库中管理。
4. `package_hash` 作为内容版本标识；另用版本记录保存 parent、时间、消息和统计。
5. `base_version_id` 做乐观并发检查。远端已变化时返回 `409 stale_base`，第一版不自动 merge。
6. 只有所有 blob、package 校验、搜索投影和 embedding 都成功后，才在一个事务中切换 active version。
7. 相同 `package_hash` 的重复 push 是 no-op，不产生新版本、不重建索引。

### 建议的上传流程

```text
rei check
  -> 构建完整 transport manifest
  -> plan(name, collection_id, base_version_id, message, files[])
  <- upload_id + missing_blob_hashes
  -> 幂等、可重试上传缺失 blob
  -> commit(upload_id)
  <- version_id + active package_hash + uploaded/reused/indexed 统计
  -> 成功后更新 .rei/remote.json
```

`files[]` 至少包含 `namespace`、`logical_path`、`sha256`、`byte_size` 和 `media_type`。package 的
`.node.md`、content 和 assets 与 raw source 一视同仁，服务端从 CAS 临时物化完整 package 后继续调用现有
1.0 validator，不能信任客户端给出的 Node 元数据。独立、公开的 hash-exists API 容易泄露对象存在性；
缺失列表应只通过已认证且限定 Collection 的 plan 返回。

提交时服务端执行：

1. 检查 `base_package_hash` 等于当前 active hash；首次发布必须为空。
2. 检查所有 manifest blob 已存在，重新校验 size/hash，物化并完整验证 package 与 sources 引用集合。
3. 服务端重算 `package_hash`，必须等于客户端声明值。
4. 对比当前和目标：resource 用 `(namespace, logical_path, sha256)`；Node 用稳定 ID、`node_hash` 以及
   path/parent/order/tree 等投影字段；不存在于目标的项为删除。
5. 只为变化 Node 重建 SearchUnit；embedding 以
   `(embedding_profile, hash(contextual_text))` 缓存复用，而不是只绑定临时 SearchUnit 行。
6. 在事务内 upsert 变化项、删除失效项、写版本记录并切换 active version。对象先落 CAS，失败产生的孤儿由 GC 清理。

### 最小服务端版本模型

建议保留当前 `collections/nodes/resources/...` 作为 active projection，新增轻量元数据：

```text
collection_versions(
  id, collection_id, package_hash, parent_package_hash,
  manifest_sha256, message, created_by, created_at, stats
)

collections.active_version_id -> collection_versions.id
```

完整版本 manifest 本身以压缩 JSON blob 存入 CAS；它引用每个 logical file 的 SHA-256。不要为每版复制一套
Node、SearchUnit、ParadeDB BM25 和 embedding 表。回滚时读取旧 manifest，重新走同一 reconcile/commit 流程；
只有未来明确要求“无需切换即可搜索任意历史版本”，才把搜索投影也按 version 隔离。

## 服务端是否保留多个版本

**建议保留，但只保留轻量快照和被其引用的内容寻址对象，不保留每版完整数据库/索引副本。**

理由：

- 增量上传本身只需要当前 manifest，但历史快照能低成本提供误发布回滚、审计和可复现性。
- 相邻版本通常共享大多数 SHA-256 blob，物理空间增加主要来自真正改变的文件。
- 已通过完整验证但语义错误的数据仍可能被发布；仅靠“失败事务保留旧当前态”无法处理这种情况。
- 无界历史会阻止对象 GC，因此保留策略必须与版本功能一起交付。

建议默认策略：始终保留 active；另外保留最近 10 个成功版本以及最近 30 天内的版本，
两者取并集。上传 session/孤儿对象 24 小时后可清理；删除版本后，只有不再被任何 active 或 retained
manifest 引用的 blob 才能删除。具体数量和天数做服务端配置，不写进 package 协议。

## 分阶段落地

### Phase 1：先解决上传带宽与可靠性

- 增加 transport manifest、plan/blob/commit 和 `base_package_hash`。
- commit 仍可先完整物化、完整验证、完整生成投影并原子替换；这样改动面较小，先证明协议和恢复能力。
- 支持 no-op、缺 blob 补传、重复 blob 幂等、上传 session TTL 和 409 陈旧基线。

### Phase 2：增量索引与 embedding 复用

- 引入服务端 projection hash/search unit hash。
- 只更新 changed/deleted Node 的关系与 SearchUnit；复用未变化 embedding。
- 对“重命名、移动、order 改变但正文未变”单独测试，避免只看 `node_hash` 漏更新 path/tree 投影。

### Phase 3：轻量历史、回滚和 GC

- 写 `collection_versions` 与 manifest blob，提供 list/show/rollback。
- 实施 retention mark-and-sweep；先标记、宽限期后删除，不在 commit 请求中同步删对象。
- rollback 创建一个新的 head 记录，指向旧内容状态；不篡改或删除原有历史链。

只有出现真实多人编辑需求后，才考虑 Phase 4 的自动 merge/rebase、branch/tag 或历史版本在线查询。

## 验收检查

- 首次 push 上传全部 blob；相同 package 再 push 上传 0 blob、创建 0 新版本、生成 0 embedding。
- 只修改一个 CSV 时，仅上传新 CSV、受影响 card/content blob，仅重建对应 Node/SearchUnit。
- 文件 rename 且 SHA-256 不变时不上传字节，但 path/tree 投影正确更新。
- 删除 Node/source 时新 active state 不再可见；历史保留期内仍可回滚。
- 两个客户端从同一 base 发布时仅第一个成功，第二个收到包含当前 hash 的 409。
- 任意 blob 缺失、hash 不符、package 无效、索引或 embedding 失败都不切换 active version。
- commit 响应丢失后重试是幂等的；过期 session 和无引用 blob 可安全 GC。
- rollback 后 pull/search/get/table query 全部读取回滚后的 active state。

## 方案澄清（人工反馈后）

### 冲突统一在本地解决

- 服务端只负责在 plan/commit 时比较 `base_version_id`，发现远端已经前进就返回 `409 stale_base`；
  它不合并 Node、card 或 raw 数据。
- 客户端取得 base、local、remote 三个 manifest，以稳定 Node ID 做三方比较。无冲突变化可在本地重放；
  同一 Node 双改、删除对修改、身份/path 冲突必须在本地解决，重新 `scan/check` 后再 push。
- commit 必须在事务锁内再次检查 base。并发失败前上传的 CAS blob 可以被下一次提交复用，过期后由 GC 清理。

### 命令使用 Git 语义，不增加 `sync`

```text
rei fetch = 只取得远端 version/manifest 到 .rei remote cache，不修改工作区
rei pull  = fetch + 在本地 fast-forward 或三方整合
rei push  = 以本地记录的 remote base 发布；过期则拒绝并要求先 pull
```

日常使用 `pull`。只有希望先 `diff`、审阅远端变化或暂时不改工作区时使用 `fetch`。首次 `pull --output`
仍相当于 clone 一个 Node-only checkout；对已有 checkout 执行 pull 才进入更新/合并流程。authoring Collection
中的 raw、`.rei` identity 和生成 content/assets 不被远端直接覆盖；只允许按稳定 Node ID 整合可编辑 card body。

### 整体回滚与部分恢复

- 整体回滚已有一个完整、已验证的目标 manifest，只需把 active projection reconcile 到该目标并生成一个新的
  rollback commit，流程确定。
- 部分恢复本质上是把旧版本的一部分 cherry-pick 到当前版本，需要重新决定 subtree 边界、parent/order、
  source/derived 关系、路径冲突和依赖闭包；它是一次合并，不是简单移动版本指针。
- 第一版只让服务端执行整体回滚。部分恢复在本地完成：fetch 旧版本、选择 Node/subtree、合入当前工作区、
  scan/check，再作为新的完整 Collection 版本 push。

`version_id` 表示提交事件，`package_hash` 表示内容。回滚不把 active 指针静默移回旧事件，而是创建一个新事件；
因此同一 `package_hash` 可以出现在原版本和 rollback 版本中，父关系必须使用 `parent_version_id`。

### 历史查询和快速回退

推荐的 B 默认只索引 active version：历史 manifest 可以 diff/pull/get，整体 rollback 后可以正常 search，
但不能同时在线搜索任意历史版本。在线历史搜索需要保留每版搜索投影，或按需建立带 TTL 的临时索引，作为后续功能。

无需另造“只保存上一次”的特殊备份格式：B 的 retained version 已经包含上一次 manifest，并共享 CAS blob。
如果回滚耗时实测不能接受，可以短期保留 active 和 previous 两套 version-scoped Node/SearchUnit/embedding 投影，
通过切换 active version 快速回退；代价是查询全部增加 version filter、索引接近翻倍、ID 隔离和 GC 更复杂，
已经接近受限的完整 revision 模型，不建议在第一版实现。

### 复杂度边界

| 能力 | 复杂度 | 首版建议 |
| --- | --- | --- |
| manifest、缺失 blob 上传、幂等 commit | 中 | 实现 |
| base 检查、fetch/pull、本地拒绝冲突 | 中 | 实现 |
| 轻量版本记录、整体 rollback、retention/GC | 中 | 实现 |
| 自动三方合并和冲突 UI | 高 | 先报告冲突，后续增强 |
| 增量 SearchUnit 与 embedding cache | 高 | 第二阶段 |
| 部分 Node/subtree cherry-pick | 高 | 后续本地功能 |
| 历史版本同时在线搜索或双投影秒级回退 | 高 | 有明确 SLA 后再做 |

整套最终形态复杂，但首版只做 manifest/CAS、乐观并发、本地冲突拒绝、轻量历史和整体回滚，属于可控的中等改造；
不应把自动 merge、部分恢复、历史在线搜索和增量索引一次性绑在首版中。

## 首版范围复审

### SearchUnit 与 embedding 增量的区别

- SearchUnit 增量：只为变化 Node 重新切分 card/content/table row，并只 upsert/delete 对应搜索行和 BM25 项；
  未变化 Node 的搜索行不动。这要求稳定 unit signature、处理行号/ordinal 变化和增量数据库约束，复杂度较高。
- embedding 增量：即使首版仍完整生成 SearchUnit，也用
  `(embedding profile/config fingerprint, SHA-256(contextual_text))` 查缓存；只调用模型生成 cache miss，
  然后完整原子替换 active projection。它不要求先实现搜索表差量写入，收益高且风险较低。

首版采用“完整物化和校验 + 完整生成 SearchUnit + embedding hash cache + 完整原子替换当前投影”。
相同 package 在进入索引前直接 no-op；单文件变化时网络只上传缺失 blob，embedding 只计算变化文本，
但 SearchUnit/BM25 仍完整重建。真实数据证明完整 BM25 重建成为瓶颈后，再做 SearchUnit 增量。

### 首版必须实现

1. 完整 transport manifest，服务端重算并验证 `package_hash`。
2. plan 返回缺失 SHA-256；blob 上传幂等、可重试；commit session 有 TTL。
3. plan 和 commit 事务内都检查 `base_version_id`；服务端只返回冲突，不执行 merge。
4. `rei fetch` 只更新 remote cache；`rei pull` 执行 fetch + 本地 fast-forward。双方都改时首版生成冲突报告并停止，
   不自动三方合并；用户本地解决后重新 scan/check/push。
5. `collection_versions`、`parent_version_id`、active pointer 和 CAS manifest；重复 package push 是 no-op，
   不创建新版本。
6. versions list/show/diff，以及按 version 的 manifest/card/resource get/pull，供审阅和本地解决冲突。
7. Collection 整体 rollback；rollback 创建新的提交事件并原子重建 active projection，之后可正常 search。
8. embedding hash cache；embedding profile 或配置变化时自然 cache miss。
9. retention、过期 upload session 清理和基于 retained manifest 的 mark-and-sweep GC。
10. commit 任一步失败都不改变 active version；CLI 只在成功响应后更新 `.rei/remote.json`。

### 首版明确不实现

- 自动 merge/rebase、服务端冲突合并。
- Node/subtree 部分回滚；以后作为本地 cherry-pick 功能。
- SearchUnit/BM25 增量写入。
- 任意历史版本同时在线搜索或临时历史索引。
- active/previous 双投影和秒级指针回退；首版始终只有一套 active 搜索投影。
- branch、tag、多人协作权限和大文件块级差分/断点续传。

这使首版仍然提供真正的增量上传、并发保护、可审计历史、整体回滚和 embedding 复用，同时避免最容易扩大
状态空间的多版本索引、自动合并和部分恢复。

首版 API 与 CLI 契约见 [`9.版本控制和增量上传-api-cli.md`](9.版本控制和增量上传-api-cli.md)。
