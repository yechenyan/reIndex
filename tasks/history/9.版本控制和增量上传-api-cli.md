## 原则

- 服务端检测 stale base、验证完整目标状态并原子提交，不做 merge、rebase 或部分恢复。
- CLI fetch base/remote manifest，在本地比较和报告冲突。
- package 仍是协议真相；transport manifest 只负责寻址缺失 blob 和重建完整 package。
- `version_id` 标识提交事件，`package_hash` 标识内容；同内容 rollback 可以产生新的 version。
- search/grep/table query 始终只读 active version。

## HTTP API

| 方法 | 用途 |
| --- | --- |
| `POST /v1/push` | 提交完整目标 manifest，检查 base，创建 upload session，返回缺失 blob |
| `POST /v1/push/blob` | 在 upload session 内上传一个缺失 blob；multipart，幂等 |
| `POST /v1/push/commit` | 再次检查 base，完整验证并原子创建 version/切换 active |
| `POST /v1/fetch` | 取得 head 或指定 version 的元数据与完整 transport manifest |
| `POST /v1/history` | 分页列出 Collection 的 retained version summaries |
| `POST /v1/pull` | 现有接口增加可选 `version_id`，下载该版本 Node-only ZIP |
| `POST /v1/get` | 现有接口增加可选 `version_id`，精确读取该版本 resource |

当前 multipart 完整 ZIP `POST /v1/push` 在 CLI/server 同步升级时改为 JSON manifest，并作为三阶段 push 的
起点；不增加只有一个调用方的 `/push/plan` 别名，也不长期保留两套发布流程。

### Push start

请求：

```json
{
  "name": "test2",
  "collection_id": "...",
  "base_version_id": "... or null",
  "message": "Initial import",
  "operation": "publish",
  "dry_run": false,
  "manifest": {
    "spec": "reindex/transport@1.0",
    "package_root": "<collection-package-directory>",
    "files": [
      {
        "namespace": "package",
        "logical_path": "index.node.md",
        "sha256": "...",
        "byte_size": 123,
        "media_type": "text/markdown"
      }
    ]
  }
}
```

响应包含 `upload_id/expires_at/head_version_id/missing_blobs/no_op`。首次发布的 base 为 null；
远端已有 head 且 base 不匹配时返回 `409 stale_base`。缺失判断只存在于受 Collection 限定的 plan，
不增加公开的 hash-exists API。

### Blob upload

`POST /v1/push/blob` 使用 multipart 字段 `upload_id`、`sha256` 和 `blob`。服务端流式计算 hash 和 size；
响应 `stored/reused`。同一请求可以安全重试；CLI 逐个上传 plan 返回的缺失 blob。首版不做块级差分或分块续传。

### Commit

请求包含 `upload_id`。服务端在 Collection 事务锁内再次比较 session base 与 active version，检查 manifest
引用的 blob 全部存在，物化并验证完整 package/source 集合，重算 package hash，复用 embedding cache，
完整替换 active projection，并创建 version。重复 commit 返回同一结果。

响应至少包含：

```json
{
  "status": "ready",
  "version_id": "...",
  "parent_version_id": "...",
  "package_hash": "...",
  "uploaded_blobs": 2,
  "reused_blobs": 14,
  "embedded_units": 3,
  "reused_embeddings": 1173
}
```

### Fetch 与 history

`POST /v1/fetch` 请求 `collection` 和可选 `version_id`；缺失时返回 active head。响应包含 version metadata、
完整 transport manifest 和 manifest hash。CLI 缓存后自行执行 local/base/remote diff，不增加服务端 diff API。

`history` 返回 `version_id/parent_version_id/package_hash/message/created_at/stats/is_active`，使用 cursor 分页。

### Rollback

不增加专用 rollback API。CLI fetch 目标 version manifest 后，以当前 head 为 base 调用正常三阶段 push；
plan 可带 `source_version_id` 和 `operation: rollback` 作为审计元数据。目标 blob 已在 CAS 中时
`missing_blobs` 为空；commit 创建新的 version event，其 package hash 可以等于旧目标版本。

## CLI

### 现有命令调整

| 命令 | 首版变化 |
| --- | --- |
| `rei push <path>` | 内部执行 plan/upload/commit；增加 `--message`、`--dry-run`，禁止 force 覆盖 stale base |
| `rei pull <name> --output <dir>` | 首次 checkout；增加 `--version` 可拉历史 Node tree |
| `rei pull --path <dir>` | 更新已有 checkout：fetch 后 fast-forward；双方都改则写冲突报告并停止 |
| `rei get <target>` | 增加 `--version`，从 retained manifest 精确取得历史 resource |

### 新命令

| 命令 | 用途 |
| --- | --- |
| `rei fetch [path]` | 取得 active version/manifest 到 `.rei` remote cache，不修改工作区 |
| `rei history [path-or-name]` | 列出 retained versions；`--version` 显示单版详情 |
| `rei diff [path]` | 默认比较 local/base；`--remote` 或 `--from/--to` 比较远端 manifest |
| `rei rollback <name> <version> --message <text>` | 先检查/fetch head，再调用整体 rollback；支持 `--dry-run` |

日常流程：

```text
rei pull --path <dir>
编辑、scan、check
rei push <dir> --message "..."
```

需要先审阅远端时：

```text
rei fetch <dir>
rei diff <dir> --remote
rei pull --path <dir>
```

首版冲突写入 `.rei/conflicts.json`；base/head manifest 保存在 `.rei/cache/remote/versions/`，本地内容保留在
工作区，不把冲突标记写进 Node YAML。用户解决并重新 `scan/check` 后运行 `pull --path <dir> --continue`
明确接受新 base，再 push；不增加 `rei sync`、服务端 merge、`--force` 覆盖或自动 resolve。

## 实现与验证

- CLI/server 已切换到三阶段 manifest/blob/commit 协议，没有保留 multipart ZIP push。
- PostgreSQL commit 在 advisory transaction lock 内二次比较 active base，并原子写 version/files、替换 active 投影。
- retention 保留 active、最近 10 版与最近 30 天版本；CAS GC 对 retained manifests 和 upload sessions 做标记。
- `test4-all` 的 5 个输入复制到临时目录，以真实 Uvicorn HTTP + CLI 跑通首传、no-op、V2 增量、stale/conflict、
  Node-only fast-forward、历史 diff/get/pull、本地继续、整体 rollback、active search/get 和 embedding 复用。
- 并发 commit 回归验证两个空 base session 中先提交者成功，后提交者返回 `409 stale_base`。
- 内存/默认验证：`uv run pytest -q`；真实环境验证使用临时
  `paradedb/paradedb:0.24.3-pg18`、正式 `init-db`、PostgresCatalog/ParadeDBSearch 和外部 Uvicorn，设置
  `REINDEX_E2E_BASE_URL`、`REINDEX_VERSION_E2E_BASE_URL`、`TEST_PARADEDB_URL` 后运行全套，结果
  `47 passed`、零跳过。最终数据库中 `test4-all` 为 4 versions、7 Nodes、1176 SearchUnits，rollback head active。
- 真实 pgvector cache 命中测试曾发现驱动返回 `Vector` 而非普通 iterable；已改用 `to_list()` 并验证
  1024 维 cache 写入/命中读取，最终数据库留有 `integration-cache@1024` 验证记录。
- Ruff format/check、compileall 和 scoped `git diff --check` 通过。

## 明确不增加

- `/merge`、`/rebase`、`/partial-rollback` 和 historical `/search` API。
- 专用 `/rollback` 或服务端 `/diff` API；两者分别复用 push、由 CLI 本地完成。
- 独立公开的 `/blobs/exists`、长期并存的完整 ZIP push、active/previous 双投影。
- `rei sync`、`rei checkout`、branch/tag 和自动三方合并命令。
